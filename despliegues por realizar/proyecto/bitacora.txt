1. LEER PRIMERO: ESTADO REAL Y OBJETIVO
======================================================================

El usuario solicitó analizar la web y la app para que trabajen como un
solo proyecto: mismas cuentas, propiedades, perfiles, favoritos, visitas,
chat y notificaciones, con datos consistentes entre ambos dispositivos.
Después del diagnóstico autorizó implementar las correcciones.

Se implementaron cambios en el código local, reglas, funciones del
servidor, pruebas y herramientas de migración. La web compila y Android
compila y pasa sus pruebas locales. Las pruebas de seguridad e integración
se ejecutaron con emuladores contra demo-ruwajay.

NO se desplegaron cambios al proyecto real de Firebase.
NO se aplicaron migraciones ni se modificaron sus documentos reales.
NO se ejecutó el SQL preparado para Supabase.
NO se publicó la web, el APK ni una versión en tiendas.
NO se demostró la entrega de push real ni GPS/audio en un teléfono físico.

Por lo tanto, el trabajo local está preparado y probado en el alcance
descrito aquí, pero todavía NO debe declararse que producción está
perfectamente sincronizada ni que todas las funciones son equivalentes.

ADVERTENCIA DE COMPATIBILIDAD: NO publicar únicamente firestore.rules.
Las visitas y la apertura de conversaciones ahora necesitan las nuevas
Cloud Functions. Publicar reglas sin servidor/clientes compatibles puede
impedir que usuarios de las versiones anteriores continúen operando.

En la última comprobación, Firebase CLI informó que no había cuentas
autorizadas en este equipo: "No authorized accounts, run firebase login".
Para continuar con producción se necesita acceso autorizado del operador.
No pedir ni recibir contraseñas de Gmail ni archivos privados de claves.

Esta bitácora agrupa el trabajo por módulos. No pretende reproducir
literalmente los ocho puntos del diagnóstico conversacional original.

4. PROPIEDADES, FOTOS, FAVORITOS, RESEÑAS Y BÚSQUEDAS
======================================================================

Propiedades:
- Los clientes consumen el catálogo real compartido en Firestore.
- Se normalizan fotografías antiguas, incluidas listas con objetos.
- Se rechazan referencias temporales como blob:localhost para persistencia.
- No se inventan precio, ubicación, fotografías o amenidades ausentes.
- Una propiedad inexistente no se sustituye por una vivienda de demostración.
- Los errores de guardar/editar ya no se ocultan como si hubiese éxito.
- Las nuevas fotografías se cargan en Firebase Storage antes de persistir
  sus URL; las URL HTTPS históricas pueden conservarse.
- La edición conserva propietario real, campos existentes y metadatos
  protegidos; el administrador no se convierte en dueño al editar.

  la ubicación permanece ausente hasta que se seleccione.
- Comparaciones web se actualizan con el catálogo y no pierden la selección
  por una primera lectura vacía de caché.

Favoritos:
- Se almacenan bajo el usuario autenticado en Firestore.
- La web informa fallos y revierte cambios optimistas cuando corresponde.
- Se quitaron dependencias de solicitudes a un backend ausente.

Reseñas:
- Ambos clientes leen/escriben la información compartida de Firestore.
- No se insertan reseñas de demostración ni se simula persistencia local.
- El éxito se muestra después de que la escritura termina correctamente.
- Android obtiene el nombre actual del perfil antes de publicar.
- No se afirma que el autor es inquilino verificado sin evidencia.

Búsquedas guardadas:
- Se guardan por usuario en saved_searches.
- Web y Android permiten guardar/aplicar; Android también lista/elimina.
- Se alinearon precio, tipo, zona y filtros básicos/avanzados.
- El último ajuste Android corrige un tipo vacío que podía devolver cero
  resultados y añade patio, seguridad y agua/cisterna a guardar/restaurar.
- Cloud Functions compara nuevas propiedades con búsquedas para avisar.

6. CHAT, LECTURA, ARCHIVOS Y LLAMADAS
======================================================================

- Conversaciones por UID; no se acredita pertenencia por email/nombre.
- ID canónico: v2_{tenantUid}_{ownerUid}_{propertyId}.
- Se reutiliza una sala histórica válida cuando corresponde para mantener
  su historial; migradas/archivadas se ocultan en los clientes.
- Los mensajes y el resumen de conversación se guardan en el mismo lote.
- lastMessageId vincula el resumen con el mensaje realmente escrito.
- Campos comunes: senderId, senderName, type, createdAt, mediaUrl.
- Tipos del contrato de datos: text, image, audio, location. La presencia
  del tipo en el contrato NO demuestra una interfaz de envío de ubicación
  idéntica y probada en ambos clientes.
- senderId debe ser el UID actual y senderName debe coincidir con perfil.
- Fotografías y notas de voz son archivos reales en Storage, con subida,
  grabación/reproducción y manejo de errores en ambos clientes.
- readAt.{uid} registra lectura por participante y sirve entre dispositivos.
- Web respeta foco/visibilidad; Android considera el ciclo de vida visible.
- El unread se limpia al leer y vuelve a aparecer con mensajes nuevos.
- Se retiraron presencia, escritura y respuestas rápidas ficticias.
- Se corrigió un fallo real de ChatPage: la propiedad aún no cargada hacía
  fallar un acceso a .id; los enlaces ahora usan el ID de conversación.
- La autoría se compara por UID, sin confiar en isUser o nombres históricos
  como "Tú" o "user".
- El estado del chat se limpia al cerrar/cambiar sesión.

Llamadas:
- Se eliminó el modal web que simulaba una llamada.
- El botón abre el marcador telefónico cuando existe número disponible.
- active_calls está cerrado por reglas.
- No hay llamadas internas WebRTC implementadas ni probadas.
- Si se solicitan, requieren alcance propio, señalización autenticada,

11. MIGRACIÓN Y SUPABASE: PREPARADOS, NO EJECUTADOS EN REAL
======================================================================

Script: functions/scripts/migrate-data.js.

Comportamiento:
- Modo dry-run por defecto.
- Respaldo recursivo de documentos/subcolecciones, incluso si falta un
  documento padre que contiene subcolecciones.
- Conserva timestamps en un formato serializable del respaldo.
- Normaliza fotos, coordenadas, visitas, slots, salas y mensajes.
- No atribuye titularidad por coincidencias de nombres/correos.
- Requiere mapeos explícitos y valida los UID referenciados contra Auth
  antes de aplicar.
- Las salas antiguas se conservan con migratedTo; los clientes usan las
  nuevas. Salas de prueba se archivan solo por decisión explícita.
- Exige decisiones sobre administradores y confirmaciones antiguas.
- Audios simulados sin grabación requieren reconocimiento explícito de
  archivo; una foto temporal o un audio inexistente no se recuperan.
- Rechaza mezcla de proyecto real y variables de emuladores.
- --apply exige respaldo de entrada, otro respaldo nuevo y cero incidencias.
- Comprueba que los documentos no cambiaron desde el respaldo revisado.
- Hasta 450 escrituras se aplican en lote atómico. Si hay más, requiere
  diseñar una migración por etapas; no existe esa estrategia implementada.

Claves del archivo de decisiones:
identities: ID anterior -> UID verificado.
properties: reparaciones de fotos/coordenadas verificadas.
adminDecisions: retain o demote para administradores existentes.
confirmedVisitIds: visitas históricas confirmadas cuya legitimidad se revisó.
archiveRooms: rutas de salas de prueba revisadas para archivar.
acceptMissingAudio: rutas de notas antiguas sin grabación aceptadas como archivo.

Comando de lectura/respaldo/diagnóstico (requiere ADC del operador):
node functions/scripts/migrate-data.js --project ruwa-jay --backup .artifacts/db-backup.json --report .artifacts/db-audit.json

Revisión offline de respaldo y decisiones:
node functions/scripts/migrate-data.js --input .artifacts/db-backup.json --mapping .artifacts/identity-mapping.json --report .artifacts/db-plan.json

Ejemplo de APLICACIÓN: no ejecutar sin respaldo revisado, incidencias
resueltas, mantenimiento y acceso autorizado al proyecto correcto:
node functions/scripts/migrate-data.js --project ruwa-jay --input .artifacts/db-backup.json --mapping .artifacts/identity-mapping.json --backup .artifacts/db-backup-before-apply.json --report .artifacts/db-apply-report.json --apply
