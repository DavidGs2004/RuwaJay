RUWAJAY — DIAGNÓSTICO DEL ERROR REACT #310
26 de octubre de 2026

RESULTADO
La causa del error publicado está identificada y reproducida. El código
local ya contenía la posición correcta del Hook antes de esta intervención.
Se verificó esa corrección, se añadieron pruebas de regresión y se preparó
un build nuevo. No se desplegó: producción seguirá sirviendo el build viejo
hasta que se publique manualmente la entrega.

1. CAUSA EXACTA Y EVIDENCIA
La consulta de solo lectura a https://expotec.duckdns.org/ruwajay/ devolvió:
  /ruwajay/assets/index-BdIg6dPC.js
  /ruwajay/assets/index-DB08556z.css
En el JavaScript publicado, función LF, línea 50, alrededor de la columna
150565 del stack, aparece SystemUpdatesModal con esta secuencia:
  useAuth()
  useState([])          // internalUpdates
  useState(true)        // internalLoading
  useEffect(...)
  if (!isOpen) return null
  useState('todas')     // selectedCategory: aquí está el problema
El modal cerrado ejecuta menos Hooks que el abierto. Al llegar un aviso,
Header cambia showUpdatesModal de false a true y React detecta el Hook extra.
Esto explica el error aunque el usuario todavía no haya iniciado sesión.
Firebase/Firestore puede desencadenar la apertura, pero la infracción es el
orden de Hooks del componente, no un fallo de autenticación o de IIS.

Referencia oficial:
https://react.dev/errors/310
https://react.dev/reference/rules/rules-of-hooks

2. COMPONENTE RESPONSABLE
web/src/components/ui/SystemUpdatesModal.jsx
El archivo local ya situaba selectedCategory junto a los demás estados,
antes del retorno por !isOpen. La revisión de Git confirma que esa versión
estaba en el commit e249567; no se atribuye como una corrección nueva.
El nuevo build emite la función PF, con los tres useState antes del retorno.
evidencia-build.txt contiene el fragmento del artefacto nuevo.
No se encontraron otros componentes locales con infracciones de orden de
Hooks en la auditoría de los 67 archivos JS/JSX de web/src.

5. VALIDACIONES EXISTENTES CON INCIDENCIAS
- Suite pública de navegador: sus 9 casos pasaron, 0 fallaron; el ejecutor
  superó 45 segundos al cerrar el webServer y se interrumpió después.
  No se presenta este comando como una ejecución con salida limpia.
- Reglas, Storage, integración y gateway: 17 pruebas; 12 pasan, 5 fallan.
  Cuatro expectativas de seguridad no coinciden con las reglas conservadas:
  privacidad de perfiles, suplantación de remitente, modificación de miembros
  y readAt ajenos, y escritura directa de llamadas. La quinta prueba intenta
  subir video/mp4, rechazado por el validador de medios actual del gateway.
- Navegador compartido: 2 pruebas; 1 pasa y 1 falla en shared-project.spec.js:58,
  al esperar que readAt alcance lastMessageTimestamp después de volver a
  poner visible el chat. El fallo observado no es React #310.
- Triggers anteriores registran errores body undefined con ciertos datos
  de pruebas. Functions declara Node 22; el equipo tiene Node 24 y emuladores
  lo advierten. No se cambiaron versiones ni lógica del servidor.
- El build advierte sobre un bundle grande y un import dinámico de Firestore
  que también se importa estáticamente. Ningún aviso impide compilar.
- Se observó un enlace a /iniciar-sesion en PropertyDetailPage, mientras la
  ruta registrada es /login. Se deja documentado sin ampliar esta corrección.

No se afirma que toda la aplicación pase sus pruebas. Las incidencias
anteriores están fuera de la corrección de orden de Hooks y no se ocultaron
relajando pruebas ni modificando reglas o permisos.
